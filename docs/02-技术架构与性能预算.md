# 02 · 技术架构与性能预算

> 第一约束：**普通的轻薄本也要能跑。**
> 这条约束不是「优化一下」的程度，而是反过来决定架构与设计：渲染必须做成三档、模拟必须与渲染解耦、**并且设计上要接受「工厂规模有上限」。**

---

## 1. 目标硬件分级

| 档位 | 参考硬件 | 分辨率 | 帧率 | 模拟 UPS | 同屏物品实例 |
| --- | --- | --- | --- | --- | --- |
| 低（最低配置） | 4 核 CPU（2018 年后）/ Intel UHD 620、Vega 8 级集显 / 8 GB RAM | 1080p，渲染缩放 0.6–0.7 | 30 | 20 | ≤ 8,000 |
| 中（推荐） | 6 核 / Iris Xe、MX450 级 / 16 GB | 1080p 原生 | 60 | 60 | ≤ 40,000 |
| 高 | 独显 / 16–32 GB | 1440p | 60+ | 60 | ≤ 100,000 |

最低配置底线：Windows 10 x64、8 GB RAM、2 GB 磁盘、集显。

**顺带一个好消息**：如果开发机也是轻薄本，Godot 本身就是轻量方案（编辑器体积与内存远低于 Unity / Unreal，导出也不需要重型工具链）。

---

## 2. 五条核心手段

1. **模拟 / 渲染彻底解耦** —— 模拟固定步长（20 / 30 / 60 UPS 三档），渲染插值。低配跑 20 UPS，CPU 压力直接减到三分之一，画面仍然 30 FPS。
2. **画质分档 + 分辨率缩放** —— 低配最关键的一个开关：缩放 0.6 等于像素量减少 64%，画质损失远小于收益。
3. **实例化与资产预算** —— MultiMesh 承载物品与传送带段，图集 + 共享材质，建筑低模 + LOD。
4. **按需生成与卸载** —— 区块流式加载、视距分级、离屏不渲染。
5. **自动降档** —— 按帧时间滑动调整渲染缩放与画质档，玩家无感，不需要手动进设置。

## 3. 每帧预算表（毫秒）

**中档（60 FPS = 16.6 ms）**

| 项目 | 预算 |
| --- | --- |
| 模拟 tick（传送带 + 机械臂 + 电网） | 5.0 |
| 渲染提交（含 MultiMesh 更新） | 6.0 |
| 区块生成 / 网格化（主线程只上传） | 1.0 |
| 逻辑电路求解 | 1.0 |
| 虫潮寻路（flow-field 分摊） | 1.0 |
| 余量（UI / 音频 / GC） | 2.6 |

**低档（30 FPS = 33.3 ms）**：模拟 8.0（20 UPS → 每 3 帧才 tick 一次）/ 渲染 12.0 / 生成 1.5 / 电路 1.0 / 寻路 1.5 / 余量 9.3。

> 规矩：任何新系统加入前，先回答「它吃多少毫秒」。答不出来就先别做。

## 4. 画质档位对照表

| 项目 | 高 | 中 | 低 |
| --- | --- | --- | --- |
| 阴影 | 方向光 4096 + 2 个动态光源 | 2048 + 1 个 | 1024 或假阴影（贴花） |
| 辉光 / 自发光 | 全屏 Bloom | 低分辨率 Bloom | 仅自发光，无 Bloom |
| 体积雾 | 开 | 简化 / 局部 | 关 |
| SSAO / SSIL / SDFGI | 全开 | 关 SDFGI | 全关 |
| 粒子 | 100% | 60% | 25%（只保留玩法相关） |
| 后处理（景深 / 色彩 / LUT） | 全开 | 部分 | 全关 |
| 视距 | 2.5 km | 1.5 km | 0.8 km |
| 物品渲染上限 | 100k | 40k | 8k |

「低档」的视觉语言要和「可读性优先」一致：**用色块、图标、轮廓代替细节**。低配不是丑，是更干净。

## 5. Godot 具体设置

- **渲染器**：Mobile（D3D12 / Vulkan，轻薄本更省）；极老机器可另出一个 Compatibility（GLES3）导出包（同一套工程，换渲染器导出）。
- **纹理**：导入为 VRAM 压缩（S3TC / BPTC）；2D 界面与建筑贴图走图集。
- **抗锯齿**：关闭 MSAA，用 FXAA / 低档 TAA 替代。
- **阴影**：单方向光 + 按档位分级；远处不投影。
- **实例化**：物品与传送带段用 `MultiMeshInstance3D`，建筑用 `MeshInstance3D` + 共享材质。
- **C# 内存**：对象池 + 严禁每帧分配（GC 抖动是低配杀手）。
- **导出**：`godot --headless --export-release "Windows Desktop" ...`

- 冷启动预期：2–5 秒。

## 7. 资产预算（硬指标）

- 单个建筑：≤ 2,000 三角形；LOD1 ≤ 400；LOD2 用公告板
- 传送带：**合并网格或 MultiMesh，禁止每段一个 MeshInstance**
- 贴图：512×512 起步，建筑共用图集（4×4 或 8×8）；透明材质 ≤ 2 种
- 不透明材质总数 ≤ 8（每个材质 = 一组 draw call）
- 音频：环境音 OGG 循环；动态音乐分层 2–3 轨，不做全交互式配乐

---

## 8. 「规模上限」的设计补偿（这是设计问题，不是技术问题）

低配机器一定会先撞上限，所以**把高分标准从「总量」改成「效率与紧凑度」**：

- 指标：单位面积产出、每台机器产出、平均物流长度、能耗比
- 游戏内 **工厂体检报告**：瓶颈、拥堵、空转、能耗，给 A/B/C 评级
- 超预算时**明确提示**（「当前规模接近本机上限，建议优化布局」），而不是静默掉帧

这样低配玩家靠「设计得更好」照样有成就感 —— 与「轻薄本能跑」的目标天然一致。

## 10. 实测结果（2026-10-10 已跑，可复现）

```bash
cd "tools/Bench" && dotnet run -c Release
```

| 规模 | 每 tick 耗时 | 占 60 UPS 帧预算 |
| --- | --- | --- |
| 5,000 段传送带 / 40,000 物品 | 0.154 ms | 0.9 % |
| 10,000 段 / 80,000 物品 | 0.300 ms | 1.8 % |
| **20,000 段 / 160,000 物品 / 200 仓储** | **0.696 ms** | **4.2 %** |

- 托管内存：**6.8 MB**（在途物品 16 万时）；tick 内平均位移 45,017 个物品/ tick
- 设计预算 5 ms/tick → 实测 0.7 ms，**约 7 倍余量**
- 结论：**低档 20 UPS 完全是浪费余量**；瓶颈从「模拟」移到了「渲染提交」与「地形分块」，下一阶段优化应转向后者

其余实测：
- 生产链：90 秒产出 46 片铁板（电力 220/105 W，效率 1.00）
- 存档往返：273 bytes，建筑与带载物品完全一致
- 蓝图：3 笔记录 → 70 字元 → 完整解回
