# 04 · 排行榜与数据方案

> 前提：**单机游戏 + 本地存档 + 没有服务器 + 未来放在 GitHub。**
> 这三条决定了一件事：排行榜必须设计成「**不需要信任玩家**」才成立。

---

## 0. 先说残酷的现实

- 本地存档 = **无法阻止改档**。任何「服务器权威验证」在没有服务器的前提下都是空谈。
- 所以排行榜的价值不在「公平竞赛」，而在**目标感、炫耀、社群话题**。
- 结论：**把排行榜设计成"过程型挑战"，而不是"信任型竞赛"。**

---

## 1. 三层榜单（什么时候用什么）

| 层级 | 时间点 | 方案 | 成本 |
| --- | --- | --- | --- |
| L0 本地榜 | v1 首发 | 自己的历史成绩、工厂档案、里程碑 | 0 |
| L1 周挑战榜 | v1 首发 | 固定种子 + **GitHub 当后端**（Issue 表单 + Actions 校验 → `leaderboard.json`） | 0（GitHub 免费额度） |
| L2 Steam 榜 | 上 Steam 后 | Steamworks Leaderboards API | 0（Steam 自带） |
| L2.5 过渡后端 | 有需要时 | Cloudflare Workers + D1/KV，或 Supabase | 免费额度足够 |

上 Steam 之后直接用 Steam 排行榜——**免运维、自带身份、自带反垃圾**，这是最优解。GitHub 方案是为「上 Steam 之前」准备的。

---

## 2. v1 方案：GitHub 当后端（零成本）

**流程：**

1. 玩家在游戏里点「提交成绩」→ 游戏生成一个**提交包**：种子、分数、指标类型、游戏版本、存档哈希、（可选）存档文件；同时生成一段可直接粘贴的 Markdown。
2. 玩家把它贴进仓库的 **Issue 表单**（`.github/ISSUE_TEMPLATE/score.yml`，字段固定，自动打 label）。
3. **GitHub Actions** 触发：
   - 校验格式、版本号
   - 合理性检查（时间 / 资源是否物理可能）
   - 可选：用提交的存档做一次离线复算
   - 通过 → 把记录合并进 `data/leaderboard.json` 并回帖；失败 → 打 `invalid` 标签
4. 游戏内排行榜直接拉取仓库里的 `leaderboard.json`（原始文件 URL），本地缓存。

**优点**：零成本、可审计、社区可复查、GitHub 账号本身就是一道防垃圾门槛。
**缺点**：分钟级延迟、提交有门槛 —— 所以**只适合周挑战这种慢节奏榜单**，不适合实时榜。

---

## 3. 校验三档（诚实标注，不假装能防作弊）

| 档 | 提交物 | 标注 | 用途 |
| --- | --- | --- | --- |
| A 自报 | 只有分数 | `自报` | 个人日常成绩 |
| B 指纹 | 分数 + 存档哈希 + 版本号 | `指纹校验` | 周挑战榜默认 |
| C 复算 | 分数 + 存档（+ 种子） | `已验证` | 头名与奖励位，由 Actions 离线复算 |

**原则：排行榜不与经济回报挂钩**（避免作弊动机）；头名只给称号与徽章。

---

## 4. 周挑战设计（v1 首发就要有）

- 每周固定三件事：**种子 + 起点条件 + 目标**
  - 例：种子 `CF-2026-W42`，起点「只有 1 台采矿机」，目标「300 秒内产出第一块合金板」
  - 或：目标「7 天内达到 1000 SPM」
- 起跑线一致 → 结果可比；作弊成本高（要改的东西太多）。
- 周榜结束后自动归档进「名人堂」，构成长期留存。

---

## 5. 指标设计（顺手解决低配问题）

不要只比「总量」——那会奖励堆机器、惩罚低配机。用这些指标：

| 指标 | 说明 |
| --- | --- |
| 紧凑度 | 单位面积产出 / 单位物流长度产出 |
| 效率 | 每台机器每分钟产出、能耗比 |
| 时间 | 达到指定里程碑的用时 |
| SPM | 无限研究时代的通用炫耀指标 |

好处：**低配玩家靠「设计得更好」也能上榜** —— 与「轻薄本能跑」的目标一致。

## 7. 隐私

- 用**匿名短码**（游戏内生成的随机 ID）或 Steam ID，**不做账号系统**。
- 明确列出上传内容：分数、种子、版本号、哈希；**存档正文可选**。
- 提供「完全离线模式」开关：不联网也能玩，不上传任何东西。
- 不做遥测（telemetry），除非玩家主动开启。

## 8. GitHub 仓库建议（呼应「文件以后都放 GitHub」）

**目录结构**

```
Core Factory -Infinite Horizon/
├── README.md
├── docs/                 # 本文档集
├── game/                 # Godot 工程（project.godot、scenes、src、data）
├── data/                 # 排行榜数据（leaderboard.json）
├── assets-src/           # Blender 源文件（走 Git LFS）
└── .github/
    ├── ISSUE_TEMPLATE/score.yml    # 成绩提交表单
    └── workflows/export.yml        # 自动导出 EXE 并附到 Release
```

**要点**

- **Git LFS** 管 `.blend / .png / .glb / .wav`（GitHub 免费 1 GB，够用）—— 大模型与纹理绝对不要直接进普通 Git 历史。
- **Actions 自动打包**：CI 里先下载 Godot 导出模板，再 `--export-release`，把产物挂到 Release；仓库里只存源码，不存 EXE。
- **版本号 = 存档版本号**：发版时同步递增，这是存档迁移的前提。
- `.gitignore` 必须排除 `.godot/`、`bin/`、`obj/`、`export/`、`*.pck`（本目录已放好）。

---

## 9. 一句话总结

**v1**：本地榜 + GitHub 周挑战榜（Issue 提交 + Actions 校验），指标用「紧凑度 / 效率」而非总量。
**上 Steam 后**：切到 Steam 排行榜，GitHub 方案退居「跨平台 / 非 Steam 玩家」的备选。
**永远不做**：账号系统、服务器权威验证、与经济回报绑定的竞赛。
