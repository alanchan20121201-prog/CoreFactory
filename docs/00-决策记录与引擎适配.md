## 二、逐项理由

### D1 引擎：Godot 4.7（Mono / C#）

**为什么不是 Electron + Three.js**（这是上一版的建议）：
上一版的技术分析是在「走 EXE → 默认 Electron」的假设下做的，其中约一半内容是浏览器特有约束（COOP/COEP、SAB 门槛、WebGL2 兜底、存储配额、多浏览器兼容）。一旦确定用原生引擎，这些约束**直接消失**，而 JS 的模拟吞吐天花板反而成了劣势。

**为什么是 Godot（对你最合适的）**：
- 你的机器上已经装了 **Godot 4.7.2 Mono** 和 **Blender**，桌面上还有 Godot 课程资料 —— 学习曲线可以复用，不用从零开始。
- 原生导出 Windows EXE，包体与启动速度都远优于 Electron（后者光 Chromium 就 100 MB+）。
- **C# 是这套系统的好选择**：强类型、JIT 性能接近原生、原生多线程（`Thread` / `Task`），复杂工厂逻辑的可维护性远高于 GDScript；对 AI 生成代码也最友好。
- 3D 实例化有现成的 `MultiMeshInstance3D`，正是「几万条传送带 + 十万物品」要用的东西。
- 需要极限性能时有 **GDExtension**（C++/Rust）这条逃生通道，不必重写整个游戏。
- 面向 Steam 发行：Godot 的 Windows 导出 + Steamworks 绑定（C# 可用 Facepunch.Steamworks）路径成熟。

**保留的退路**：模拟核心写成**不依赖 Godot 类型的纯 C#**（见下方「工程约定」）。万一将来要换引擎或搬进 GDExtension，这一层可以整块搬走 —— 这让 D1 这个决定是可逆的。

**明确不选**：
- Tauri（Windows 下 WebView2 版本碎片不可控，模拟得靠 Rust，AI 支援度与迭代速度都下降）
- Unity（体积、授权、调试复杂度都不划算，且与已完成的 JS 分析完全不兼容）

### D2 视角：默认第三人称，可自由切换

- 工厂游戏的核心动作是**精确摆放**：第一人称在密集建筑区会出现遮挡与判位困难，第三人称 + 可缩放至近俯视，才是「建造视角」。
- 第一人称保留三种用途：驾驶机甲/载具、沉浸式巡视工厂、拍摄模式。
- 额外做**俯视设计模式**（像看图纸）：专门用来规划大布局、摆放蓝图幽灵。
- 成本提示：三种视角共用同一套相机控制器，切换成本很低，是「加一个开关」而不是「做三个游戏」。

### D3 联机：暂不做

- 实时联机要求 bit 级确定性 + 服务器架构，会把全部开发拖慢一倍。
- 异步社交（P5 榜单 / P6 周挑战 / 蓝图市场 / 工厂快照）能拿到约 80% 的社交价值，成本只要 10%。
- 但**确定性设计照做**（固定步长 + 种子化 PRNG），作为将来的可选项——反正它对存档与 bug 复现也有好处。

### D4 Mod：v1 不支持脚本 Mod

- 任意脚本 Mod = 安全沙箱 + 确定性 + 版本迁移三重灾难，对个人项目是净负担。
- 替代方案：**所有数值数据表化**（配方、建筑、科技、生物、掉落全部放数据文件，代码只读数据），将来把这层数据暴露成可外部加载的目录，就得到「免代码 Mod」。
- UGC 的重心放在**蓝图与模块**（M3），传播价值比 Mod 高得多。

### D5 首发群系：3 个（每个有独占资源 + 独占威胁 + 独占视觉）

| 群系 | 定位 | 独占资源 | 独占威胁 | 视觉 |
| --- | --- | --- | --- | --- |
| 孢子森林 Sporewood | 生物质路线 + 生物驯化（M8）主产地 | 木材、纤维、有机物 | 孢子云、虫群 | 发光孢子、巨型菌林 |
| 水晶高地 Crystal Reach | 高级材料 + 晶体科技（M7） | 稀有金属、三种晶体 | 失控机械守卫 | 矗立晶柱、反射光斑 |
| 液态金属盆地 Molten Basin | 重工业 + 高能耗冶炼 + 地热 | 液态金属、地热能源 | EMP 潮、钻地虫 | 流动金属湖、热浪扭曲 |

## 三、浏览器方案 → Godot 替换表

| 原方案（Electron / 网页） | Godot 4.7（C#）对应做法 |
| --- | --- |
| 主线程只渲染，模拟放 Web Worker | 主线程渲染，模拟放独立 `Thread`；用双缓冲数组或 `ConcurrentQueue` 交换数据 |
| SharedArrayBuffer 双缓冲 | 共享 C# 数组 + 双缓冲；**不再需要 COOP/COEP** |
| COOP/COEP 响应头、coi-serviceworker | 完全不需要，直接删除 |
| `InstancedMesh` | `MultiMeshInstance3D` |
| 无状态渲染（顶点着色器算物品位置） | `ShaderMaterial` + MultiMesh 的 per-instance 数据（`set_instance_custom_data()`），同样在 shader 里算位置 |
| WebGL2 / WebGPU 双后端 + GPU 兼容测试 | Godot 的 Vulkan/D3D12 后端 + 兼容（Compatibility）渲染器；仍需做图形分级 |
| IndexedDB / OPFS 存档 | 原生文件 I/O，`user://`（实际落在 `%APPDATA%`），直接写二进制 |
| Worker 里做贪婪网格化 | 后台线程 + `SurfaceTool` / `ArrayMesh` 生成区块网格 |
| WASM 逃生通道 | **GDExtension**（C++ / Rust）原生扩展 |
| electron-builder + NSIS 打包 | `godot --export-release "Windows Desktop" CoreFactory.exe` |
| electron-updater | Steam 自动更新，或自建轻量更新器 |
| 浏览器版本碎片 / 存储配额 / 首包下载 | 全部不存在 |

**结论：设计层的结论（带段+槽位模型、区块串流、贪婪网格化、种子+增量存档、蓝图版本化、flow-field 寻路、性能预算制）全部保留；只有「怎么实现」的那一层换了对象。**

## 四、工程约定（现在就要定死）

1. **模拟核心 = 纯 C#，不引用任何 Godot 类型**。放独立命名空间（如 `Core.Sim`），可单元测试、可移植、将来可搬 GDExtension。
2. **固定步长 tick（60 UPS）**，渲染帧与模拟帧解耦；所有随机数走种子化 PRNG。
3. **一切数值数据表化**：配方 / 建筑 / 科技 / 生物 / 掉落 全部在数据文件，代码只读数据（这是 D4 的前提）。
4. **存档 = 世界种子 + 被改动区块的增量 + 元数据**（版本号、迁移器），二进制格式，非 JSON。
5. **蓝图 = 版本号 + 建筑列表 + 连线 + 端口 + 参数占位**，压缩后字符串；旧版本必须能迁移或明确报错。
6. **性能预算制**：给「每帧毫秒」做预算表，任何新系统都要报自己吃多少预算。
